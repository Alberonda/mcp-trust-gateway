# MCP Trust Gateway — real overhead benchmark

Generated by `scripts/benchmark_gateway_overhead.ts` against real Jira/SonarQube
servers, real local embeddings, real Postgres (Neon) — not synthetic data. Read-only
tool calls only. Every number below is computed directly from this run's own data, not
asserted. A dated snapshot of one real run — re-run the script for current numbers
rather than trusting this indefinitely.

## Conclusions — the good and the bad, computed from this run

- ✅ Through the gateway with a warm cache, a 1-server session used 7663 tokens on average vs. 23997 tokens connecting directly (-68% change) — find_tool's ranked top-K result is genuinely far smaller than a raw tools/list dump of every real tool.
- ✅ Through the gateway with a warm cache, a 2-server session used 10150 tokens on average vs. 29861 tokens connecting directly (-66% change) — find_tool's ranked top-K result is genuinely far smaller than a raw tools/list dump of every real tool.
- ⚠️ Total wall-clock latency for a 1-server session: 11329ms through the gateway vs. 9606ms connecting directly (18% change). The gateway is measurably SLOWER end to end here — the token savings do not come for free. Most of both numbers is the real upstream API's own response time, not gateway overhead, but the gap is real.
- ⚠️ Total wall-clock latency for a 2-server session: 13422ms through the gateway vs. 7702ms connecting directly (74% change). The gateway is measurably SLOWER end to end here — the token savings do not come for free. Most of both numbers is the real upstream API's own response time, not gateway overhead, but the gap is real.
- ✅ The first call_tool against a server with an EXPIRED catalog entry averaged 6778ms, vs. 7229ms with an already-warm one (6% difference). Close enough to call the background refresh genuinely invisible to the caller, as designed — it never blocks the response the agent is actually waiting for.
- ⚠️ find_tool against an already-warm catalog averaged 1503ms (range 756-2608ms) across 10 calls. That's much higher than the ~1ms embedding + one cache read the design assumed — not yet root-caused (candidates: per-process embedding-model cold start, or Neon's network round-trip for a hosted, remote Postgres). Worth a real instrumented breakdown.
- ⚠️ Deliberately oblique queries found the intended tool on the FIRST find_tool call only 3/10 times (30%). This benchmark's retry uses a query the script already knew was good — a real agent has no such guarantee, so a real miss rate could translate directly into tools that are simply never found.
- ⚠️ Of 7 retries (with clearer, known-good phrasing), 1 STILL missed the intended tool. An oblique-enough query can defeat even a reasonable rephrasing — this is a real reliability gap, not just a hypothetical one.
- ⚠️ Each retry added roughly 504 tokens and 962ms on top of the failed first attempt — a real, non-trivial cost per miss, not a rounding error.
